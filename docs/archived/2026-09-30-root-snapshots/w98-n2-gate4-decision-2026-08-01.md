# W98 N-2 件 4 双门控阈值主拍决策

日期：2026-08-01  
范围：纯文档与 memory 调研；不修改 production code、测试或 alembic。

## §1 结论摘要

本报告复核 W89 件 4 双门控历史，并对 W98 已落地 PR/路线提交做实测抽样。结论是：继续使用“件 4a 老核心 unchanged + 件 4b 派工 brief 授权范围”的主门控，同时把 wc-l 与语义行数作为件 4b 的双轨预警指标，而不是单独的硬否决条件。推荐方案为 **B（双轨阈值）+ C 的老核心保护语义**，即 v10.2 的可执行版本。

不可逆警告：阈值一旦写入派工模板，会影响后续是否允许合并；因此本报告只提出可回滚的文档规则，不改变现有代码门禁，也不把历史偏差追认为“默认许可”。任何超过阈值的变更仍必须停下、据实上报并由主拍明确授权。

## §2 件 4 双门控历史回顾

W89 DERIVE-09 首次把“wc-l 行数”与“语义行数”分开。真实样本为：PR1 `knowledge_service.py` wc-l=13、语义=2；PR4 `hybrid_retriever.py` wc-l=130、语义=100；PR7 `hybrid_retriever.py` wc-l=53、语义=32。旧的 wc-l≤1 会把三个样本全部判为失败，说明纯物理行数不能代表授权范围。

W89 的主拍改良为：件 4a 检查老核心函数 unchanged，件 4b 检查文件是否在 brief 明列且变更类型是否被授权。该规则保留了 0 production code 的边界，又避免把新增函数、import、注释和兼容 alias 误报成违规。

P2-GATE W98 的真实案例进一步验证了漂移问题：`micro_bubble_agent.py` 派工预期小于 200 行，实测 wc-l=294；拆分为抽取 132 行与 alias/兼容等 162 行，仍在 brief 的抽共享函数与兼容授权内。该案例应被记录为“阈值超出但授权范围成立”，而不是纸面 PASS。

## §4 三个候选方案

### 选项 A：wc-l≤1

优点是最直观、最严，适合纯文档同步或单字符修复。缺点是 W89 三个样本 0/3 通过，P2-GATE 的 294 行授权抽取也会被机械否决；它把 import、上下文、alias 和新增函数体全部混在一起。继续作为唯一门控会诱发 agent 隐瞒真实改动或拆分提交，故不推荐。

### 选项 B：wc-l≤30 + 语义行数≤N

优点是可审计、可预警，并同时约束物理扩散和业务语义。建议 N 按变更类型分层：微改 10，模块新增 30，大型重构 100。超过任一值不自动失败，而是触发 brief 复核、文件级 diff 和主拍授权。风险是“语义行数”必须逐段定义，不能由 agent 自报；应由 reviewer 按 def、分支、schema、测试夹具等类别记录。

### 选项 C：件 4a only

优点是保留老核心 unchanged 这一最强安全边界，最大限度降低回归风险。缺点是取消件 4b 后，派工范围失去硬约束，新模块可能无界扩张。它只适合成熟的 v11 派工和高度信任的 agent，不适合作为 v10.2 默认规则，故不单独推荐。

## §5 三维主拍依据

1. **历史分布**：W89 的 13/53/130 与 P2-GATE 的 294 证明 wc-l≤1 不适配真实重构；W98 新模块总量 329–603 也说明必须区分文件级和提交级。
2. **v10.1 稳定性**：双门控已能解释 PR1/4/7 的误报，并成功保留老核心 unchanged；但语义阈值尚未统一，v10.2 需要把分层数字写入 brief。
3. **P2-GATE 偏差**：294 对 brief<200 是 47% 超出（按 200 基准），即使授权成立也不能抹平偏差。偏差必须进入反馈段并要求下一批预估方法改进。

## §6 推荐与阈值表

推荐 **B + C 保护语义**：件 4a 是硬门；件 4b 是双轨预警与授权门。

| 变更类型 | wc-l 上限 | 语义行数上限 N | 超限动作 |
|---|---:|---:|---|
| 纯微改/文档伴随代码 | 30 | 10 | 停止合并，补 diff 解释 |
| 单模块新增 | 30 | 30 | 主拍复核文件清单 |
| 已批准大型重构 | 100 | 100 | 必须拆阶段或追加授权 |
| 跨模块/跨层提交 | 不适用提交总量 | 按文件分别计算 | 禁止用总量掩盖单文件 |

P2-GATE 294 不满足上述常规 wc-l，但历史授权仍有效；它是校准样本，不是新默认上限。

## §7 v10.1 → v10.2 升级建议

- brief 必须同时列出目标文件、老核心 def 清单、预计 wc-l 和预计语义 N。
- reviewer 必须输出 `wc-l / +/- / semantic / authorization` 四列，禁止只报 PASS。
- 语义行数定义为实际新增或修改的 def、分支、schema、序列化字段和行为断言；注释/import 单列，不计入语义 N，但计入 wc-l。
- 超限只允许“据实上报 + 主拍复核”，不能自动放宽。
- 件 4a 与件 4b 结果分开记录，避免“授权成立”覆盖“老核心变化”。
- 每批至少抽样 10 个 PR；不足 10 个必须明确样本不足。

## §11 可执行测量协议

以下协议用于避免“语义行数”成为主观数字。

1. 基线必须是派工 brief 指定的 base SHA，不允许用移动中的 `main` 替代。
2. 物理行数记录 `git diff --numstat <base>..<tip> -- <file>` 的新增与删除之和。
3. wc-l 记录完整 unified diff 的行数，仅作为展示成本指标。
4. 语义新增包括新增 def、分支、返回字段、配置行为和持久化行为。
5. 语义修改包括改变既有条件、调用顺序、异常语义、权限或状态转换。
6. import、空白、纯注释、类型注解不计语义行，但必须计入物理行数。
7. 兼容 alias 单独列为 compatibility，不与新业务语义混计。
8. 新测试只验证授权范围，不反向证明 production 变更被授权。
9. 同一逻辑搬移时，删除与新增不可简单相加为新增语义；应标注 move/refactor。
10. reviewer 必须附命令与 base/tip，禁止只贴汇总数字。

建议命令：

```bash
git diff --numstat <base>..<tip> -- <file>
git diff --unified=0 <base>..<tip> -- <file>
git diff --unified=0 <base>..<tip> -- <file> | grep -E '^[+-](async )?def |^[+-](class |if |elif |return )'
```

## §12 主拍判定矩阵

| 件 4a | 件 4b 阈值 | brief 授权 | 决策 |
|---|---|---|---|
| PASS | 未超 | 明确 | 可合并 |
| PASS | 超限 | 明确 | 停止并复核，主拍可显式放行 |
| PASS | 任意 | 不明确 | 拒绝，补派工授权 |
| FAIL | 任意 | 明确或不明确 | 拒绝，除非新派工改变老核心边界 |

该矩阵防止两类错误：一是把“未超阈值”误当授权；二是把“brief 授权”误当成件 4a 老核心变化的豁免。

## §13 类 20.32 建议文本

**类 20.32 件 4 阈值与授权错配**：当 wc-l 或语义行数阈值与派工 brief 的真实授权范围不一致时，agent 必须同时报告物理行数、语义行数、老核心变化和授权证据。阈值超限不自动失败，阈值未超也不自动通过；最终由件 4a 老核心硬门与件 4b brief 授权共同决定。历史超限案例只用于校准，不得被提升为默认额度。

## §14 决策有效期与复审

v10.2 建议先试行三批，每批至少收集十个 PR/路线样本。三批后按误报率、漏报率、主拍例外率复审：误报率超过 20% 时调整 wc-l 展示阈值；漏报任一老核心违规时立即回滚到件 4a 强制人工审查；主拍例外率超过 30% 时说明分层数字失真，应重新按业务类型分组。未完成复审前，不把建议阈值写成 CI 自动拒绝规则。
