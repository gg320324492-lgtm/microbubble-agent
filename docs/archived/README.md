## 二、为什么归档文档里保留着旧密码串（不要"顺手清掉"）

2026-10-09 的 DB 密码轮换（L-14）把仓库里的硬编码旧值清零后，**仍有 7 个文件 12 处**保留着轮换前的旧 DB 密码字面量。这是**有意保留**，理由三条：

1. **它们是事故复盘的历史原文，删掉就失真。**
   这些文件记录的是"当初为什么会写错"——比如 `w-n-glitchtip-fix-attempt-2026-08-05.md:41` 写的
   就是当时那条真实报错连接串。把密码抹掉，读者就无法复现当初的排查路径，事故也就失去了教材价值。
   这与本目录整体定位一致：**档案的价值恰恰在于它记录了当时真实的样子**。

2. **旧值已轮换失效，不构成凭据泄露。**
   密码已轮换（证据：拿旧值连库精确复现 `InvalidPasswordError`，换 `.env` 现值即通过）。
   已失效的字面量无法用于认证，跟"有效凭据躺在仓库里"是两件事。

3. **删改档案会让归档与 git 历史对不上。**
   这些文件是 git tracked 的，改动会让"归档 = 某个时点的原样快照"这个属性失效，
   而这正是归档区存在的理由。

## 三、自查时的正确判定（重要：不是看总数是否为 0）

**不要**用"全仓 grep 命中总数 == 0"作为 L-14 的验收标准 —— 那样会诱导人把档案改写，
而档案一旦被改写就失去意义（见上）。

正确的判定是这三条**同时**成立：

| # | 判定项 | 当前状态（2026-10-09 实测） |
|---|---|---|
| 1 | **活代码 / 活配置 / scripts / tests / CI workflow 中零命中** | ✅ `git grep` 全仓 12 处命中，**无一落在** `app/` `web/src/` `alembic/` `scripts/` `tests/` `.github/` `docker-compose*.yml` |
| 2 | 剩余命中**全部是历史性文档**（归档区 + memory 复盘 + 未生效的历史设计稿） | ✅ 7/7 文件均为此类（清单见下节） |
| 3 | 剩余命中**全部是已失效的旧值**，无当前有效凭据 | ✅ 旧 DB 密码已于 2026-10-09 轮换 |

> 补充：gitleaks 的路径 allowlist（`.gitleaks.toml`）本就放行 `docs/.*\.md$`，
> 所以这些 `.md` 不会被 secret scan 拦下；`.yml` 历史设计稿**不在**该放行名单内，
> 它能通过是因为其中的字面量没有命中任何 gitleaks 规则，而不是被路径豁免。

## 五、纪律

1. **不删改归档正文**。要补充说明，在本 README 里写，或新写一份，不动原文。
2. **新的一次性产物**完成即归档到本目录或对应批次子目录（口径见 `docs/README.md` 写文档的纪律）。
3. **归档不豁免真实凭据**：若哪天归档文件里混进了**仍然有效**的密码 / token，
   那是事故不是档案，立即轮换该凭据，并按 `.gitleaks.toml` 流程处理，不要用"它在归档区"当理由放着。
