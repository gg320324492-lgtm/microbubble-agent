## 零、先说结论（TL;DR）

1. **问题范围比预想窄得多，也更极端**：网盘 326 个活跃文件里 **295 个是 .pptx（90.5%）**，其他扩展名合计 31 个且**几乎不含图片**（docx/xlsx 实测 0 图）。多模态问题 ≈ PPT 问题。
2. **单 chunk 不是「文本太少」而是「文本全挤在一个 chunk」**：235 个单 chunk pptx 的 chunk 里**有真实文本**（中位 1912 字符、中位 15 页 `[PAGE:N]` 标记）。真正的盲区是**图片里的内容完全没进索引**。
3. **最关键证据**：`1537`（48 页）的 chunk 总文本 **33 个字符**，而第 3 页是一张拍摄投影幕布的照片，上面写着「INB-GTSH 模型成功地预测了床层中气泡的生长和破裂过程」——这段内容**现在 100% 搜不到**。
4. **MiniMax-Text-01 直接吃 `image_url`**，实测 **5.1 秒/页**，转写近乎逐字。ollama `qwen2.5vl:7b` 也能跑但 **67.3 秒/页**（慢 13 倍）。容器里**没有任何 OCR 库**。
5. **每页只需取最大那张图**（160/160 页验证为整页幻灯片截图），其余是几十 KB 的装饰图 —— 所以调用数 = 页数，不是「图数 ÷ 页数」。
6. **只做最盲的前 20 个文件 = 400 页 = 全量工作量的 11.2%**。

### 1.4 ⚠️ 顺带查出的三个索引缺陷（比图片更紧急，需主拍确认）

这三条不是本次任务范围，但会直接改变「做不做多模态」的收益判断：

| # | 现象 | 出处 SQL | 影响 |
|---|------|----------|------|
| A | **278 / 326 个 drive 文件 `search_text` 为空**，仅 48 个有值 | `SELECT count(*) FILTER (WHERE coalesce(search_text,'')='') ... FROM knowledge WHERE storage_mode='drive' AND deleted_at IS NULL` → `326 / 278 / 48` | BM25 / tsvector 通道对网盘内容**基本失效**（向量通道另算，见下） |
| B | **`knowledge.content` 只有 29–37 字符**，形如 `[drive upload] 2025.9.22.pptx` | `SELECT id, length(content) ... ORDER BY file_size DESC LIMIT 12` | 主表检索字段几乎是空的 |
| C | `knowledge.embedding` 仅 **48/326** 有值，但 `knowledge_chunks.embedding` **1067/1067 全部有值**（覆盖 324 个文件） | `SELECT count(*), count(*) FILTER (WHERE embedding IS NOT NULL) FROM knowledge_chunks WHERE knowledge_id IN (...)` → `1067 / 1067 / 324` | **向量检索对 chunk 是通的**，坏的只是 BM25 侧 |

> 解读：单 chunk ≠ 没被索引。文本确实进了 chunk 且有向量。**真正的盲区是图片内容**，外加 BM25 侧的空 `search_text`。
> 修 A（回填 `search_text`）很可能比做多模态**更便宜、见效更快**，建议主拍单独立项。

### 2.1 三条密度结论

1. **几乎每页都有图**（`pic_pages ≈ pages`，仅 `2763`/`1260` 例外）。
2. **docx / xlsx 实测 0 内嵌图** → 这 7 个文件**不需要多模态**，只需确认现有文本索引是否够用。
3. **每页只需取「最大的那张图」**。对 1537 / 1268 / 1540 共 160 页实测：

| 文件 | 页数 | 总图数 | 图/页 | 最大图为整页截图(>500k px) | 非最大图中位像素 | 非最大图 >500k px |
|------|-----|--------|-------|----------------------|--------------|-----------------|
| 1537 | 48 | 186 | 3.88 | **48/48** | 10,000 | 0 |
| 1268 | 32 | 82 | 2.56 | **32/32** | 39,195 | 20 |
| 1540 | 80 | 163 | 2.04 | **80/80** | 39,195 | 1 |

典型页结构（1537 第 3–6 页，每页完全一致）：
```
[[1624362 B, 1702x1276],  ← 整页幻灯片照片（真正要 OCR 的）
 [ 46617 B,  871x45  ],    ← 页眉 logo 条
 [  2808 B,  100x100 ],    ← 图标
 [  2808 B,  100x100 ]]    ← 图标
```
→ **VLM 调用数 ≈ 页数**，而非图片总数。按 235 个文件 3,559 页计，约 **3,559 次**调用（不是 ~9,000 次）。
→ **例外**：`1268` 有 20 张非最大图 >500k px（真实数据图）。这类文件建议取「每页 top-N 大图」而非只取 1 张。

### 2.2 规模换算（页数取自 chunk 内 `[PAGE:N]` 标记计数）

```sql
-- pages = (length(content) - length(replace(content,'[PAGE:',''))) / 6
WITH s AS (SELECT k.id, (SELECT count(*) FROM knowledge_chunks c WHERE c.knowledge_id=k.id) nchunk,
   (SELECT length(c.content) FROM knowledge_chunks c WHERE c.knowledge_id=k.id LIMIT 1) chars,
   (SELECT (length(c.content)-length(replace(c.content,'[PAGE:','')))/6
      FROM knowledge_chunks c WHERE c.knowledge_id=k.id LIMIT 1) pages
 FROM knowledge k WHERE k.storage_mode='drive' AND k.deleted_at IS NULL
   AND lower(k.file_name) LIKE '%.pptx')
SELECT nchunk<=1 AS single, count(*), sum(pages), avg(chars::numeric/pages) FROM s GROUP BY 1;
```

| 分组 | 文件数 | **总页数** | 平均字符/页 |
|------|-------|-----------|------------|
| 单 chunk | 235 | **3,559** | 176.1 |
| 多 chunk | 60 | 233 | 266.9 |
| 合计 | 295 | **3,792** | — |

单 chunk 组页数分位：**中位 15 页 / p90 23 页 / max 80 页**。
**单 chunk 文件占全部页数的 93.9%（3559/3792）。**
