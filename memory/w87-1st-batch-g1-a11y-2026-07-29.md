## 3. e2e 真实结果 — 50 passed, 但这个绿不可信 ⚠️

跑法 / 结果 (BASE_URL=http://localhost, 本机 nginx :80 实测 200):

```
npx playwright test -c tests/visual/a11y/playwright.a11y.config.mjs --update-snapshots
  → 50 passed (1.7m)   # 25 baseline 生成 + 25 scan
npx playwright test -c tests/visual/a11y/playwright.a11y.config.mjs
  → 50 passed (1.6m)   # 复跑比对, baseline 稳定 0 漂移
```

**为什么不可信**:
- 无 `TEST_TOKEN` 时: 5 个路由 **全部**被 router 守卫重定向到 `http://localhost/login`,
  每个 baseline 记的都是登录页 → `color-contrast [serious] ×3`
- 试 `TEST_TOKEN=mock` (docs/CLAUDE-history.md:5169 历史用法): 守卫过了, 但 5 个路由
  **全部**落到 `http://localhost/dashboard` → 统一 `color-contrast [serious] ×12`
- 两条路径下 "5 个不同页面" 扫的都是同一个 DOM. 25 个 baseline 文件的 md5 互不相同,
  仅因为头部写了 page/project 名; **violations 段完全一样**
- 结论: 当前 baseline 只锁住了"登录页的 3 处对比度", 对 ChatViewSSE / drive /
  MobileChatView / MobileTaskTrash / DesktopCommentThread **零覆盖**

**未取真 token 的原因**: `/api/v1/auth/login` 实测存在 (POST 空账号 → 401, 非 404),
但带 Redis ZSET 限流 5 次/5 分钟 (`app/api/v1/auth.py:65-90`), 且无可用测试账号凭据.
不猜密码撞限流 (会波及真实登录). 需主指挥给测试账号或给 `create_access_token` 签发脚本.

## 5. 派工 v6 §5 反馈 — 类 20.25 新增

**类 20.25 "a11y 测试必先 baseline, 后修漂移"** —
baseline 模式本身正确 (首跑 `--update-snapshots` 生成, 后跑比对), 但本次实战暴露
**前置条件比 baseline 机制本身更关键**:

1. **baseline 生成前必须验证"扫到的是目标页"** — 断言 `page.url()` 落在预期路由,
   否则 25 个 case 全绿而实际扫了同一张登录页 (本次即如此). 建议 W88 把
   `expect(new URL(page.url()).pathname).toBe(expectedPath)` 加成硬断言
2. **SPA + router 守卫项目, a11y 扫描的前置是可用登录态** — 不是 axe 装配问题.
   `TEST_TOKEN=mock` 能骗过前端守卫但骗不出真实页面 (后端 401 → 前端兜到 dashboard)
3. **"全绿"在 a11y 任务里是可疑信号** — 一个真实项目首次接 axe 通常有 violation;
   0 violation 优先怀疑没扫到东西
4. 类 20 派工前提错配再一次实证: 本任务 6 处 brief 与实测不符, 均据实上报,
   **不擅自扩** (不改 playwright.config.js / 不改 web/src) **也不擅自缩** (装配 + 50 case 照做)
