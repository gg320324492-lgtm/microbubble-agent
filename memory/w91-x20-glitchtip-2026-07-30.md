## 1. 根因 (据实, 4 件排查)

### 1.1 docker ps -a — 两个实例, 只有一个崩

```
NAMES                               STATUS                          IMAGE
microbubble-agent-glitchtip-dev-1   Restarting (1) 17 seconds ago   glitchtip/glitchtip:6.2.2
microbubble-agent-glitchtip-1       Up 16 hours                     glitchtip/glitchtip:6.2.2
```

**关键**: 同名前缀两个容器, 一崩一好。只看整串输出里有 `Up` 会误判成健康 (见 §5 类 20.24 实战)。

### 1.2 docker logs — 精确报错

```
django.db.utils.OperationalError: pool error: Error occurred while creating a new object:
  db error -> db error -> FATAL: database "glitchtip" does not exist
SQL: SHOW server_version_num
```

Django 启动即连库 → 库不存在 → exit 1 → `restart: unless-stopped` → 无限重启。

### 1.3 docker inspect — 崩溃规模 + 归属

```
ExitCode=1  Error=""  RestartCount=865
project=agent-w89-p4-playwright-real
workdir=E:\agent-w89-p4-playwright-real
net=agent-w89-p4-playwright-real_default
```

**据实上报 (重要)**: 崩的 `glitchtip-dev-1` **不属于主仓库 compose 项目**, 而属于**遗留 worktree 栈**
`agent-w89-p4-playwright-real` (W89-P-4 playwright 任务留下的)。容器名带 `microbubble-agent-` 前缀
是因为 compose 里写死了 `container_name`, 与实际 project 标签不一致 — 极易误判归属。

### 1.4 db 状态 — 三个 postgres 各自独立

| postgres 容器 | 有 glitchtip 库? | 对应 glitchtip 状态 |
|---|---|---|
| `agent-w89-p4-playwright-real-db-1` | ❌ 无 | Restarting ×865 |
| `funny-mccarthy-fdad1b-db-1` | ✅ 有 | Up 16 hours |
| `microbubble-agent-db-1` | ❌ 无 | (该栈无 glitchtip 在跑) |

**根因锁定**: `docs/sentry-setup.md` §2 把建库写成"首次装机手动跑一次"。
新 worktree 起栈时人跳过这步 → 必崩。健康那个栈之所以健康, 正因当初手动跑过。

**排除项** (逐一实测排除, 不猜):
- 环境变量: `DATABASE_URL` / `SECRET_KEY` / `GLITCHTIP_DOMAIN` / `PORT` 全在, 无缺
- 镜像 tag: `glitchtip/glitchtip:6.2.2` 存在且能拉起 (同 image 另一实例 Up 16h)
- 端口: 8001 无占用, 且报错发生在绑端口之前
- compose 配置: dev / base 两份 glitchtip 段均正确 → **不需要改**

## 2. 修法 (最小修法, 派工 v3 双锚定)

### 2.1 建库 (立即解崩)

```bash
docker exec agent-w89-p4-playwright-real-db-1 psql -U postgres -c "CREATE DATABASE glitchtip;"
docker restart microbubble-agent-glitchtip-dev-1
```

### 2.2 加幂等 bootstrap 脚本 (防回归) — `scripts/glitchtip-ensure-db.sh` (新)

为什么要脚本而不是只建库: 手动步骤跳过一次就崩 865 次。脚本幂等, 可无条件在起容器前跑。

- 先查 `pg_database` 再 `CREATE DATABASE` (CREATE DATABASE 不支持 `IF NOT EXISTS`, 幂等只能靠先查后建)
- `set -euo pipefail` fail loud
- 建完**复检** pg_database, 不只看 CREATE 的 returncode (类 20.30 精确断言精神)
- 支持 `DB_CONTAINER=` 直接点名容器 / `COMPOSE_FILE=` 切栈 / `GLITCHTIP_DB_NAME=` 换库名

### 2.3 未动 docker-compose.dev.yml (据实)

派工 brief 列了修法 B/C/D (改环境变量 / 改镜像 tag / 改端口)。**实测均不适用** —
配置本来就是对的, 改任何一处都是擅自扩大。**0 production code 改动守恒**。

## 5. 派工 v6 §5 反馈 — 类 20 沉淀

### 类 20.101 (新增, 本任务主沉淀)

> **"docker service crash 排查必 4 件: `docker logs` / `docker inspect` / env 校核 / db 状态"**

四件缺一不可, 且**顺序有讲究**:
1. `docker logs --tail` 拿精确异常 (本例直接给出 `database "glitchtip" does not exist`)
2. `docker inspect` 拿 ExitCode + RestartCount + **compose project 标签** (本例暴露容器归属遗留 worktree 栈)
3. env 校核 — 逐项排除, 不猜
4. db 状态 — `psql -lqt` 列库, 多栈并存时必须逐个 postgres 都看

**本例若只做第 1 件**: 会知道库缺, 但会在**错误的 postgres** 上建库 (主仓库 db 而非遗留栈 db), 崩溃不解。
**第 2 件的 project 标签是关键** — `container_name` 写死会让容器名与实际 compose project 不一致, 只看名字必误判。

### 类 20.102 (副沉淀)

> **"手动装机步骤必须脚本化 + 幂等, 否则跳一次崩到底"**

`docs/sentry-setup.md` §2 建库写成"首次手动跑一次" → 新 worktree/新机器/重建 volume 各踩一次 → RestartCount=865。
凡文档里出现"首次启动前执行一次"的步骤, 都应配幂等脚本, 让它可以被无条件重复调用。

### 类 20.24 实战 (复用)

> "并行 agent 各自 PASS, 集成 e2e 红于隐藏假设"

本例变体: **同前缀多实例并存时, 整串 stdout 子串匹配会被健康实例掩盖崩溃实例**。
断言必须**逐行**判定。这是 brief 模板断言假绿的直接原因。
