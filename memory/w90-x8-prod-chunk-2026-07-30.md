## 调研结论 (摘要)

- W89-X-24 留口的"8 routes 走 desktop SPA fallback 而非 mobile chunk"**不是 chunk 切分问题**, 而是 **运行时 viewport 初始化 race condition**.
- 现状 vite `manualChunks` 已正确把 mobile/desktop 物理隔离 (3 + 1 chunks: element-plus-desktop / nutui-mobile / echarts / paper-adapter).
- 真正问题: `resolveMobileComponent` 在每个路由工厂函数里调用 `useViewportRef()`, 但 `useViewport()` 的 `attach()` 第一次被调用的时刻 **晚于** 路由首次解析的时刻 → 冷启动时 `width.value === 1280` (default desktop) → 8 路由被错误地解析为 desktop module. 仅 `/dashboard` 因为某种执行路径差异凑巧正确解析为 mobile (待深查).

## 步骤 3 - 调研 visual-regression + 8 routes 走 desktop SPA fallback 根因

### 8 routes vs 1 route PASS 现状

W89-X-24 记忆 + visual-regression spec 数据:

- 9 路由 (CORE_ROUTES): `/dashboard` `/knowledge` `/chat` `/tasks` `/meetings` `/settings` `/workspace?tab=projects` `/workspace?tab=members` `/project-stats`
- W89-X-24 实测: 仅 `/dashboard` PASS (5/5 RUN), 其余 8 路由走 desktop SPA fallback.

### 路由级 mobile/desktop 双栈实现 (web/src/utils/resolveMobile.js)

```js
const desktopModules = import.meta.glob('@/views/**/*.vue')
const mobileModules = import.meta.glob('@/views/mobile/**/*.vue')

function isCurrentlyMobile() {
  if (typeof window === 'undefined') return false
  try {
    const ref = useViewportRef()
    if (ref?.value?.width !== undefined) {
      return ref.value.width < MOBILE_BREAKPOINT  // 768
    }
  } catch { /* ignore */ }
  return window.innerWidth < MOBILE_BREAKPOINT
}

export function resolveMobileComponent(desktopPath, mobilePath) {
  return defineAsyncComponent(() => {
    const isMobile = isCurrentlyMobile()
    const target = isMobile && mobilePath
      ? mobileModules[resolveKey('mobile/', mobilePath)]
      : desktopModules[resolveKey('', desktopPath)]
    // ... fallback 到 desktop 若 mobile 不存在
  })
}
```

### 关键观察 (根因推测)

**双 `import.meta.glob`** 已保证 Vite 把 desktop + mobile views **全部**打包进产物. 所以"chunk 切分"角度 mobile chunk **存在**. 8 路由走 desktop 不是因为 mobile chunk 缺失.

#### 推断根因: viewport `attach()` race + `defineAsyncComponent` 工厂调用时机

1. `useViewport()` (web/src/composables/useViewport.js:67) 在第一次被调用时同步 `attach()`, 读取 `window.innerWidth` 写入 ref `width.value`.
2. 默认初始值 `width: 1280` (web/src/composables/useViewport.js:36), server-side 时无 window.
3. `resolveMobileComponent` 在 vue-router 解析路由时被触发调用 — 此时 `defineAsyncComponent` 工厂函数执行, 调 `isCurrentlyMobile()` → 调 `useViewportRef()` → **触发** `useViewport()` → 触发 `attach()` → 读 `window.innerWidth`.
4. 理论上应工作. 但若此时 `useViewport()` 还没被其他代码先调过, `attach()` 是首次执行, **应**读正确的 width.

**然而** 关键观察: 如果路径上 `vue-router` 启动 → router 守卫 → 注入 main.js 顶部的 userStore 等 → `useViewport` 还没 attach, ref 是 1280, 等守卫结束后跳到 `/dashboard` 解析器 → `isCurrentlyMobile()` → `useViewportRef()` → 调 `useViewport()` → 触发 attach → 改 width.value 为 390 → **但 defineAsyncComponent 工厂函数已经返回了 desktop 引用** (闭包捕获了 isMobile = false).

Vue 的 `defineAsyncComponent` 工厂函数**只在第一次 resolve 时跑一次**, 后续 route 切换不会重新调用工厂. 即使 viewport 后来变成 mobile, 已挂载的 desktop 组件不会被替换.

但 `/dashboard` 也能被这个机制命中才对... 除非: `useViewport()` 在某个全局代码先被调过 (例如 main.js 顶部初始化 store 时), 后续路由解析时 `width.value` 已经是正确宽度. 那么 `/dashboard` 凑巧命中是因为某个执行路径差异.

#### `/dashboard` 凑巧 PASS 的 3 个可能原因 (待 deep dive)

1. **main.js 注入顺序差异**: `useUserStore()` 可能调 `useViewport()` 在 router 解析之前, 后续所有路由的 isCurrentlyMobile 正确.
2. **PR5 RAGEvaluator 路由穿透触发顺序**: W91 +7 commit `cb5c98498` 在 router index.js 末尾加 `/admin/rag-eval`, 但 `useViewport` attach 顺序可能因 routeList 长度变化而异.
3. **巧合**: W89-X-24 只跑了 1 路由 5 RUN (PASS 5/5), 其它 8 路由**完全没跑** (W89-X-24 文字: "其余路由走 desktop SPA fallback"). 没"为什么 /dashboard 单挑 work"的精确证据.

## 步骤 4 - 调研 vite manualChunks 策略: 已正确

### vite manualChunks 配置评估

- `manualChunks` 函数当前只处理 **node_modules** (EP/NutUI/echarts) + 2 个 utils (paperAdapter/chemFormat).
- **完全没动** `src/views/` 路由代码的 chunk 归属 — 这意味着 Vite 按默认行为处理:
  - 动态 import (`() => import('@/views/...')`) → 各自独立 chunk (code-split 由 webpack/rollup 自动)
  - `import.meta.glob('@/views/**/*.vue')` → **全部**打入同一个 chunk (Vite 处理 glob 的方式)

#### 验证: 31 个 mobile vue + 39 个 desktop vue = 70 vue 文件

```
./web/src/views/Dashboard.vue (desktop, 25KB)
./web/src/views/mobile/MobileDashboard.vue (mobile, 15KB)
./web/src/views/mobile/mobile-workspace/MobileWorkspaceView.vue (mobile workspace container)
./web/src/views/mobile/chat/MobileChatView.vue (mobile chat)
... 31 个 mobile *.vue 总计 ~600KB
... 39 个 desktop views/*.vue 总计 ~2MB
```

`import.meta.glob('@/views/**/*.vue')` 把全部 70 个 vue 文件都 join 进 entry chunk (通常叫 `index-XXXX.js`), **不**走 code-split. `import.meta.glob('@/views/mobile/**/*.vue')` 类似进另一个 chunk 或同 chunk.

#### 现状推论

prod build 后:
- 入口 chunk `index-XXXX.js` **包含全部 70 个 desktop + mobile views 路由代码** (因为双 glob).
- `defineAsyncComponent` 拿到的是 glob 注册表的 **Promise()** — 引用相同的已加载 chunk, 实际代码**早就**全在内. 没有"按需加载"能力被发挥.
- `nutui-mobile` chunk 仅包含 NutUI 库 + 用 NutUI 的 mobile 组件, **不含** mobile views 本身 (因为 mobile views 是用了 NutUI **后** 的产物, 不被 manualChunks 命中).

### 所以 "8 routes 走 desktop fallback" 不是 chunk 切分问题

8 routes 走 desktop 的真因 (结合步骤 3 推断):
- 冷启动**首次**路由解析时 viewport ref 未正确初始化 → desktop module 被 select
- mobile module 在 chunk 中**已存在** (能 import), 但选中的是 desktop
- 视觉表现: 看到的是桌面版 SPA 缩小到 390px viewport, 不是 Native 移动端 UI → 视觉回归 baseline 比对 diff 3-6% > 0.2% 门禁

## 步骤 5 - 修法选项 (不擅自动)

### 选项 A — 改 vite.config.js manualChunks 按路由分组 (PR #3 实测不必需)

- **目标**: 让 mobile views 进独立 chunk (e.g. `views-mobile-XXXX.js`), 与 desktop views 物理隔离.
- **实现**: 在 manualChunks 函数里加 `if (id.includes('src/views/mobile/')) return 'views-mobile'`
- **预期收益**: 桌面端首次访问不下载 mobile views, 减小 desktop index chunk ~600KB.
- **不解决真因**: viewport race 仍存在, mobile chunk 仅在 width.value 已 correct 时才被 import, 否则仍走 desktop chunk (不过降到 0 desktop 下载).
- **风险**: 改 vite.config.js → 触发 manifest 路径变更 → 触发 PWA cache-bust 整链 (CLAUDE.md 永久锚点 "npm run build 唯一合法"); 0 production code 改动铁律**可能破** (vite.config.js 算不算 production code 有争议, 主拍决策).

### 选项 B — 拆 main bundle 让 mobile 走独立 chunk

- **目标**: 同 A 但更激进 — 把 desktop views 与 mobile views 完全物理隔离到不同入口 (多 entry).
- **实现**: Vite 多 entry 配置 (`build.rollupOptions.input`), 桌面 build 出 `desktop.html`, 移动 build 出 `mobile.html`. nginx 根据 User-Agent 路由.
- **预期收益**: 桌面端**永远**不下载 mobile views, 移动端**永远**不下载 desktop views.
- **不解决真因**: 同样 viewport race 问题.
- **风险**: 完全重构 — 改 routing 架构, 改 nginx 配置 (部署必动), 改 docker volume 挂载. **大规模工程**, 不适派工 brief v3 "只调研".

### 选项 C — 用 dynamic import 让 mobile 路由按需加载

- **目标**: 改 `resolveMobile.js`: 不再用 `import.meta.glob`, 改 `if (isMobile) return () => import('@/views/mobile/...')` 形式动态 import.
- **预期收益**: 移动端按需加载 mobile chunk, 桌面端完全不下载 mobile 代码.
- **不解决真因**: viewport race 仍存在 (代码层面没变).
- **风险**: **改 resolveMobile.js 是改业务代码** (CHANGELOG.md 已注明 "PR #3 关键修复: 用 import.meta.glob 替代 @vite-ignore"). 改回去等于回滚 PR #3 修复.

### 选项 D — 接受现状

- **现状评估**:
  - 8 routes 走 desktop SPA fallback 在 390px viewport 下仍**功能完整** (桌面版 SPA 缩小到 mobile, 元素有点挤但能点击使用).
  - **不是 critical bug** — 用户用桌面浏览器访问 /dashboard 在 mobile, 仍能登录/点击/完成核心任务.
  - 视觉回归 0.2% diff gate 误判为 flaky → W89-X-24 已修 spec 等 waitForSelector + body text > 10, **功能性正确** 但**视觉 non-pass**.
- **结论**: 若主拍决策优先级是"功能 > 视觉", 可接受 D.
- **不修成本**: 视觉回归 visual-regression 9 路由仅 1 /dashboard 截图能过 baseline 对比, 8 路由 baseline 永远 diff > 0.2%. CI 永远红.
- **建议**: 若必须 CI 绿, 须走 A 或 C. 若 CI 不必须绿 (本地跑 visual 验证), D 可接受.

### 选项 E (列出供参考, 不主推) — 修 viewport attach race (从根因修)

- **目标**: 改 `useViewport.js` 在 main.js 顶部 (或 App.vue `setup()`) **显式 `attach()` 一次**, 让 `width.value` 在 router 解析前就正确.
- **预期收益**: 根因修, 8 routes 全部正确选中 mobile/desktop 模块.
- **实现**: `main.js` 顶部 `import { useViewport } from './composables/useViewport'; useViewport()` (调用一次触发 attach).
- **风险**: 改 `main.js` + `useViewport.js` 都是改业务代码 (web/src/composables/ + web/src/main.js), 0 production code 铁律破.
