## §1 类 20 #33 —— "新增 ORM" 实为已有模型的补全关系

### 错配事实

| 项 | 内容 |
|----|------|
| brief 写 | 新增 `app/models/kg_entity.py` — kg_entity ORM（`entity_name` / `entity_type` / `knowledge_id` FK / `vector` / `first_seen_at` / `last_seen_at` / `mention_count`） |
| 仓库实情 | `app/models/knowledge_entity.py` **已存在**：`KnowledgeEntity`（**SPO 三元组**：`subject`/`predicate`/`object`/`condition`/`confidence`/`source_knowledge_ids` ARRAY/`occurrence_count`/`embedding` Vector(1024)）+ `EntityCoOccurrence`（共现网络） |
| 错配类型 | **存在性 + 语义模型错配**（brief 假设"KG 从 0 建"，实际已有 2 ORM + 5 服务共 1645 行） |
| 验证命令 | `ls app/models/ \| grep -i entity` / `grep -rn "class Entity\|class Knowledge Entity" app/models/` |

### 处置（不擅自改 brief 语义）

**关键判断：字段语义不同 → 互补非替代**，与 PR5 处置 `RAGEvaluationReport` vs 已有 `RAGEvaluation` **完全同款模式**：

| 维度 | `KnowledgeEntity`（已有） | `KGEntity`（PR8 新增） |
|------|------------------------|---------------------|
| 语义 | SPO 三元组（**关系断言**） | 扁平实体（**命名实体本身**） |
| 主键语义 | subject + predicate + object | entity_name + entity_type |
| 知识关联 | `source_knowledge_ids` ARRAY（多来源） | `knowledge_id` FK（单一，可 CASCADE） |
| 计数 | `occurrence_count`（三元组出现） | `mention_count`（实体提及） |
| 建表 | lifespan `create_all`（**0 alembic**） | **alembic 091** |

→ 新建 `kg_entities` 表，alembic 091 **0 改** `knowledge_entities` / `entity_co_occurrence`。

### 纪律（新增子铁律）

- **§1.1 "新增 ORM" 必先 `ls app/models/` + `grep "class .*Entity"` 真查** —— brief 说"新增"不代表仓库没有近义模型。
- **§1.2 发现近义模型时必做字段语义对照表** —— 字段语义不同 → **互补新建**（PR5/PR8 模式）；字段语义相同 → **必打回主拍**（重复建表是 schema 债）。
- **§1.3 互补新建时 alembic 必 0 改老表** —— 尤其老表走 `Base.metadata.create_all` lifespan（**无 alembic 迁移**）时，新迁移绝不能"顺手补建"老表（会与 `create_all` 冲突）。
- **§1.4 lifespan `create_all` vs alembic 双轨必在 runbook/SCHEMAS 明示** —— 本项目 `knowledge_entities` / `entity_co_occurrence` / `rag_evaluations` 均走 `create_all`，`kg_entities` / `knowledge_chunk` / `rag_eval_reports` 走 alembic。混淆会导致"表明明在但 alembic 查不到"。

### 处置

| # | 处置 | 依据模式 |
|---|------|---------|
| 2a | **不新建**"实体抽取"钩子（已存在），改为 Step 5 **之后**追加 **Step 5b**，**复用** Step 5 的 SPO 产物派生扁平实体（**0 新增 LLM 调用**） | PR2 chunk hook / PR3 tsvector hook 同模式（Step 内 try/except 独立容错） |

### 纪律（新增子铁律）

- **§2.1 "仅新增 X path/入口" 必先 grep 该能力是否已存在** —— `grep -nE "    (async )?def " <目标文件>` 列全类方法后再判断。
- **§2.2 能力已存在时走"并列新路"不走"改老路"** —— 新路必满足：(1) 默认可关（`enable_X=False` 时行为**等价原实现**）(2) 失败静默降级返原结果 (3) 模块级而非类方法（件 4a 语义最强守恒）。
- **§2.3 "入口"命名歧义必按件 4a 语义最强解释** —— brief 写 `_add_entity_links`（下划线前缀暗示类方法），但类方法会进老类体。虽然 `grep '^[+-]def'` 对缩进 def 不匹配（技术上仍 0），**语义上已弱化"老核心 unchanged"**。→ 采用**模块级函数** + 保留 brief 命名 + 导出无下划线别名。
- **§2.4 复用已有 pipeline 产物优于重算** —— PR8 复用 Step 5 的 LLM 三元组抽取产物派生扁平实体，**0 新增 LLM 调用**（省 token + 省延迟，满足召回侧 P95 ≤ 100ms 门禁）。派工 brief 若未提"复用"，agent 应主动选复用路并据实上报。
- **§2.5 顺序依赖必在 runbook 明示** —— Step 5b 必排在 Step 5 **之后**（`_extract_flat_entities` 读 `knowledge_entities.source_knowledge_ids`，Step 5 未写入时读空 → 0 实体，**顺序倒置即静默失效**，无报错最难查）。
