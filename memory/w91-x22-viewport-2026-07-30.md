## 3. 阻断 2 — 根因假设实测证伪 (决定性)

### 3.1 brief/W90-X-8 的假设

> "冷启动时 `width.value === 1280` 默认 desktop → 8 路由误选 desktop module"

### 3.2 实测反证 (源码)

`useViewport.js:35-39` — `viewport` ref 是**模块级 eager 初始化**, 不是 lazy:

```js
const viewport = ref({
  width: typeof window !== 'undefined' ? window.innerWidth : 1280,   // ← 浏览器里永远走 innerWidth
  height: typeof window !== 'undefined' ? window.innerHeight : 720,
  dpr: typeof window !== 'undefined' ? window.devicePixelRatio || 1 : 1,
})
```

`1280` 只在 `typeof window === 'undefined'` (SSR) 时生效。本项目 `vite.config.js` **无 `ssr:` 配置**, `index.html` 是 `<div id="app"></div>` + `<script type="module" src="/src/main.js">` — **纯 SPA, window 恒存在**。故 1280 分支在生产**永不可达**。

### 3.3 实测反证 (真跑 vitest probe)

临时 probe (跑完已删除, 未提交):

```js
window.innerWidth = 390            // 冷启动模拟 iPhone 14
const mod = await import('../useViewport.js?probe=1')   // 全新模块图
const ref = mod.useViewportRef()   // resolveMobile.js 实际走的路径, 不调 useViewport()/attach()
expect(ref.value.width).toBe(390)  // ✅ PASS — 不是 1280
```

**结果: 1 passed**。即**完全不调用 `attach()`**, `useViewportRef().value.width` 依然正确读到 390 → `390 < 768` → `resolveMobile` 选 **mobile**。

**race 不存在。brief 的修法即使能跑 (它不能), 也修不了任何东西。**

### 3.4 补充: `useViewportRef()` 本就不触发 attach

```js
export function useViewportRef() { return viewport }   // line 187-189, 无副作用
```

`resolveMobile.js:31` 用的正是 `useViewportRef()`。它从来不依赖 `attach()` — `attach()` 只负责**后续** resize/orientation 监听, 与**首帧初值**无关。这是 W90-X-8 推断链的断点。

**4 条具体规则**:

1. **推断 ≠ 根因**: 调研 memo 里出现 "NOT EXECUTED" / "推测" / "待深查" 字样时, 其结论只能作为**待验证假设**进入下一轮**调研**, 不能进入**实施**。
2. **修法代码必须 grep 验证 API 存在**: brief 给的 `viewport.attach()` 若在写 brief 时跑一次 `grep "^export" useViewport.js` 即可发现不存在。**凡 brief 含具体代码, 必先验证其调用的符号已 export**。
3. **根因必须能复现成红灯**: 修之前先写一个**失败**的测试证明 bug 存在 (本任务的 probe 反而绿了 → 证伪)。无法复现红灯 = 不存在该 bug。
4. **上游依赖未合并要先查**: 本任务预期的 X-24 spec 改良**根本不在 main**。派工前必须 `grep` 目标文件确认前置 commit 已落地, 不能凭上游 agent 的报告 (类 20.29 "必须 worktree 实测" 的同源实战)。
