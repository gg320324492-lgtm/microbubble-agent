# 第一部分：项目总体目标

## 1. 最终建设目标

将现有桌面端 Agent 从"具备本地文件操作能力的聊天 Agent"逐步建设成为：

**能够持续执行复杂科研任务、可靠使用本地工具、追踪研究证据、生产可编辑科研成果，并在异常中断后恢复执行的科研 Agent 工作台。**

系统最终必须具备以下核心能力：

1. **可靠执行：** 多轮工具调用、长任务、执行取消、上下文管理、运行恢复。
2. **工具扩展：** 本地文件、文档处理、受控代码执行、MCP、科研数据工具。
3. **科研智能：** 材料理解、文献分析、科学证据账本、实验数据分析。
4. **成果生产：** 科研报告、论文草稿、数据图表、机理示意图、DOCX/PDF/LaTeX。
5. **质量控制：** 引文核验、数值一致性检查、独立审阅、版本比较。
6. **用户控制：** 权限确认、任务干预、暂停恢复、产物审阅、数据隐私。
7. **工程成熟：** 自动化测试、可观测性、版本迁移、备份恢复、稳定发布。

## 2. 重要架构边界

- Desktop Agent 与 Server Agent 保持两套独立运行时。
- 两端将来可以共享 Agent 事件和工具协议，不强制共享执行引擎。
- 保留桌面端既有的 ReAct Loop、Tool Registry、Model Gateway、权限策略、上下文裁剪、Abort 与工作区文件围栏。
- 不把 PaperSpine 的独立 Web/Runtime 整体嵌入 Electron。
- Skill 是能力与工作流定义，Task Runtime 才是统一执行和持久化权威。
- 任何模型、Skill 或 MCP 工具都不能绕过用户授权直接访问任意文件、网络或系统命令。
- 原始科研数据默认只读；生成文件放在明确授权的输出位置。
- 不以"文件已生成""工具运行成功"直接宣称科研内容正确。

# 第二部分：三大开发阶段

## 第一大阶段：核心开发阶段

**阶段代号：P1 — Foundation & Functional Agent**

### 阶段目标

完成 Desktop Agent 2.0 的新执行底座，打通第一个真实科研任务闭环。

这一阶段的最终目标不是完成复杂论文系统，而是让小气首次拥有：

**一个能够被创建、执行、暂停、恢复、修改和审查的持久化科研任务。**

### 第一阶段分为四批

| 批次 | 建设主题 | 关键交付 |
|---|---|---|
| **P1-B01** | Task Runtime 基础建设 | 协议、数据库、状态机、事件、运行恢复、基础 UI |
| P1-B02 | Skill Host 与受控工具建设 | Skill 注册、能力授权、材料绑定、科研文档读取 |
| P1-B03 | 科研证据与基础成果建设 | 来源索引、Evidence Ledger、证据摘要、基础报告生成 |
| P1-B04 | 科研任务工作台闭环 | 阶段进度、产物版本、人工决策、修改与导出 |

### 第一阶段最终验收

完成后，用户应当能够：

1. 在桌面端选定一个包含科研材料的工作区。
2. 创建一项独立科研任务。
3. 让 Agent 读取被授权的 PDF、CSV、Excel 等资料。
4. 生成可定位来源的科研证据摘要。
5. 生成至少一份可编辑的研究报告。
6. 对成果提出修改意见并生成新版本。
7. 在任务执行过程中关闭客户端，重新打开后继续任务。
8. 查看工具执行、授权和成果变更记录。

**阶段完成标准：** 至少一条真实科研材料任务端到端运行成功，所有关键写入均有审计依据，异常恢复不重复已完成副作用，旧版聊天 Agent 功能无回归。

## 第二提升阶段：科研智能与专业能力提升

**阶段代号：P2 — Scientific Intelligence & Workflow Enhancement**

### 阶段目标

在第一阶段稳定运行的基础上，提升科研工作的深度、效率、可信度和专业成果质量。

这一阶段重点吸收 PaperSpine 的科研方法体系，同时继续参考 Claude Code、OpenCode 的工具和多 Agent 能力。

### 第二阶段计划四批

| 批次 | 建设主题 | 主要任务 | 验收成果 |
|---|---|---|---|
| P2-B01 | 文献研究与引用系统 | 文献检索、DOI/元数据、去重、BibTeX、引用和论断关联、来源质量核验 | 可追溯文献综述与引用清单 |
| P2-B02 | 科研数据与专业图表 | 受控 Python、统计分析、数据来源映射、科研图、图注、可编辑图源 | 实验数据到可编辑科研图表 |
| P2-B03 | 专业科研 Skills 与独立审阅 | 论文写作、科研配图方法、方法审阅、证据审阅、版本修改 | 有实际审阅依据的科研成果 |
| P2-B04 | Agent Harness 深度提升 | 专业 Subagent、模型能力路由、上下文压缩、MCP、任务依赖调度 | 高质量、可控的复杂科研协作 |

### 第二阶段特别要求

**1. Subagent 按需要启动，不建立固定的庞大 Agent 团队。**

可以逐步引入：

- Literature Researcher
- Data Analyst
- Writing Agent
- Evidence Reviewer
- Methods Reviewer
- Figure Reviewer
- Editor

主 Agent 保持任务控制权；子 Agent 只承担受约束的子任务，并提交真实产物和审查结果。

**2. 将科学证据约束贯穿写作与绘图。**

论文里的重要数值、图表、结论应能够关联到来源、实验条件和验证状态。

必须明确区分实验事实、文献知识、模型推断和科学假设。

**3. 不做形式化的质量通过。**

独立审阅不能只输出"优秀""通过"，需要指出具体文件、章节、图表位置、问题和依据。

**4. 成果必须可编辑。**

至少覆盖 Markdown、DOCX、PDF；根据实际需求完善 LaTeX、SVG 和科研绘图源文件。

### 第二阶段最终验收

选择若干组真实或经过授权脱敏的科研资料作为评测任务，完成：

**材料收集 → 文献研究 → 数据分析 → 论点选择 → 论文/报告草稿 → 科研配图 → 引用核验 → 独立审阅 → 修改交付。**

整个任务保留证据与版本历史；未被证实的科学论断不得被自动标记为已验证。

## 第三完善成熟阶段：稳定性、可靠性与产品成熟

**阶段代号：P3 — Reliability, Security & Product Maturity**

### 阶段目标

从"具备强大能力"提升到"可长期稳定使用、升级、恢复、维护"的成熟科研 Agent 产品。

### 第三阶段计划四批

| 批次 | 建设主题 | 主要任务 | 验收成果 |
|---|---|---|---|
| P3-B01 | 执行安全与权限完善 | 工具隔离、文件和网络权限、MCP 安全、敏感数据保护、Prompt Injection 防护 | 系统级安全验收 |
| P3-B02 | 长任务稳定性与恢复 | 崩溃恢复、工作进程清理、版本迁移、备份恢复、升级回滚、Windows 长路径 | 长期运行及故障恢复验收 |
| P3-B03 | Agent 质量评测与优化 | 科研任务基准集、事实性评测、工具成功率、恢复率、Token 与成本观测 | 可重复的质量基线 |
| P3-B04 | 成熟产品与生态 | Skill 包管理、受控更新、兼容性、用户体验、发布与运维文档 | 可持续维护的稳定版 |

### 第三阶段重点

#### 安全

- 文件、命令和网络操作遵守明确的资源授权。
- 第三方 Skill/MCP 按可信级别隔离。
- 模型不得把文献或工具输出中的不可信指令当成用户授权。
- 高风险操作有可核对的预览、授权和审计证据。
- 私有研究材料不得未经授权上传到第三方。

#### 稳定性

- Electron 异常关闭后任务可恢复。
- 失败的工具操作不会无限重复。
- 软件更新不能破坏任务、工作区和已有成果。
- 支持旧任务 Schema 和事件 Schema 的迁移。
- Windows 文件系统、文件占用、长路径和后台进程退出均纳入测试。

#### 质量

建立固定的科研基准任务，评测：

- 材料读取准确性
- 数值与单位一致性
- 引用定位准确性
- 工具执行成功率
- 中断恢复正确性
- 文档与图表交付完整性
- 审阅问题定位能力
- 成本和执行效率

### 第三阶段最终验收

交付一套有版本管理、自动化验证、明确权限、安全边界、故障恢复和标准发布流程的 Desktop Agent 稳定版本。

# 第三部分：当前正式派发的第一批任务

# P1-B01：Task Runtime 基础建设

**批次状态：待开发**
**建设级别：第一大阶段 / 第一批**
**目标：把现有桌面端会话式 Agent 扩展为可靠、可持久化、可恢复的任务型 Agent。**

这一批是整个 Agent 2.0 的地基。

**本批明确不做：** PaperSpine 全量移植、复杂文献搜索、任意 Shell 执行、Python 沙箱、多 Agent 协作、完整论文工作流和全新模型系统。

## P1-B01-T01：建立 Agent 2.0 架构契约

**优先级：P0**

### 设计任务

在桌面端建立统一的 Task、Run、Stage、Operation、Approval、Artifact、Checkpoint 类型契约。

必须清楚区分：

- `Task`：用户持续拥有的一项工作。
- `Run`：一次执行尝试。
- `Stage`：工作流中的实际工作单元。
- `Operation`：具有唯一身份的工具副作用操作。
- `Approval`：用户针对操作或资源的授权。
- `Artifact`：任务生成的版本化成果。
- `Checkpoint`：可恢复的已验证状态。

定义统一事件 Envelope：

```ts
interface AgentEventEnvelope<T> {
  schemaVersion: 1
  taskId: string
  runId: string
  seq: number
  timestamp: number
  event: T
}
```

事件至少覆盖：

- 任务与运行开始
- 阶段开始、完成和失败
- 工具操作准备、提交和失败
- 授权请求与决策
- 成果发布
- 检查点提交
- 运行终止和异常恢复

事件名称使用稳定的字符串标识，不直接依赖 UI 文案。

### 建议文件

- `apps/desktop/src/shared/agent-task.types.ts`
- `apps/desktop/src/shared/agent-events.types.ts`
- `apps/desktop/src/shared/agent-contracts.ts`
- `docs/desktop-agent-2/architecture.md`

### 验收标准

1. 所有状态与事件有明确类型定义。
2. 非法事件、缺失字段和不支持的版本被识别。
3. 不把模型的逐 Token 流式输出全部当作持久化任务事件。
4. 当前普通聊天协议仍然可用。
5. 类型测试通过。

**优先级：P0**

基于现有 `better-sqlite3` 和 `main/db/migrations.ts` 建立任务持久化结构。

## P1-B01-T03：Task 状态机与阶段执行契约

**优先级：P0**

### 设计任务

建立可测试的纯 TypeScript 状态机。

Task 负责表示工作整体状态，Run 负责记录每次执行，Stage 负责具体阶段。

建议覆盖：

- 创建
- 已规划
- 执行中
- 等待用户输入
- 等待用户授权
- 暂停
- 验证中
- 完成
- 失败
- 取消
- 异常中断
- 恢复核对

不得允许随意修改状态字段跳过状态机，例如从 `CREATED` 直接写成 `COMPLETED`，却没有任何阶段或成果依据。

第一批只需要最小阶段顺序和依赖接口，不要求马上实现复杂的动态 DAG、多 Agent 调度。

### 建议文件

- `main/agent/orchestration/task-state-machine.ts`
- `main/agent/orchestration/stage-contract.ts`
- `main/agent/orchestration/task-orchestrator.ts`

### 验收标准

1. 合法状态转移成功。
2. 非法转移失败且不修改数据库。
3. 失败的 Run 不会自动删除其所属 Task。
4. 未完成必要阶段时不能宣称任务完成。
5. 暂停、停止和失败有不同语义。

## P1-B01-T04：RunStore 与事件日志

**优先级：P0**

### 设计任务

建立统一的事件追加与任务状态持久化入口。

设计原则：

**一次业务状态更新及对应事件写入，必须在同一 SQLite 事务中完成。**

禁止出现：

- 阶段显示已完成，但没有对应完成事件。
- 事件显示已提交，但关联的状态更新失败。
- 两个并发写入获得相同的事件序号。
- Renderer 重复订阅造成事件重复执行。

要求提供：

- `createTask`
- `startRun`
- `appendEvent`
- `transitionStage`
- `commitCheckpoint`
- `getTaskSnapshot`
- `listTaskEvents(afterSeq)`

这些是建议接口语义，具体命名允许在实现时调整，但事务保证不可取消。

### 建议文件

- `main/agent/runtime/run-store.ts`
- `main/agent/runtime/event-journal.ts`
- `main/agent/runtime/task-snapshot.ts`

### 验收标准

1. 模拟事务中途失败，数据库无半提交状态。
2. 事件严格有序且具备唯一身份。
3. 能从持久化记录重新构建任务状态视图。
4. 重复事件或重复提交不会导致状态重复推进。
5. 事件中不存储 API Key、敏感令牌或完整隐藏推理。

## P1-B01-T05：工具操作日志与幂等保护

**优先级：P0**

### 设计任务

在现有 Agent Tool Registry 周围建立持久化 Operation Journal。

不替换现有工具注册表，而是在有副作用的工具调用前后建立操作状态。

建议状态：

`PREPARED → EXECUTING → COMMITTED`

异常时进入：

`FAILED / UNKNOWN / RECONCILE_REQUIRED`

每个有副作用的操作应记录：

- Operation ID
- Task ID / Run ID
- 工具名称
- 规范化参数摘要
- 授权记录
- 执行前的相关资源状态
- 结果摘要
- 可核验的执行结果
- 审计信息

第一批优先覆盖已有工作区文件写入工具，随后扩展删除、回滚等操作。

需要特别考虑三个故障点：

1. 操作登记后、实际写入前崩溃。
2. 文件已写入、数据库尚未确认时崩溃。
3. 数据库已确认、UI 尚未收到消息时崩溃。

不能通过简单的"失败就重试"处理这些情况。

### 建议文件

- `main/agent/runtime/operation-journal.ts`
- `main/agent/runtime/operation-reconciler.ts`
- `main/agent/runtime/tool-execution-adapter.ts`

### 验收标准

1. 工具副作用发生前已有 Operation 记录。
2. 已完成写入不会因恢复而被再次盲目执行。
3. 无法判定结果时显示明确的不确定状态。
4. 原有文件备份、diff、回滚、审计行为保持有效。
5. 现有权限确认机制没有被新包装器绕过。

## P1-B01-T06：Checkpoint 与异常恢复

**优先级：P0**

### 设计任务

为持久化任务建立可验证的检查点机制。

每个 Checkpoint 至少包含：

- Task 和 Run 身份
- 当前已完成阶段
- 已确认的用户选择
- 工作区绑定信息
- 输入材料摘要
- 已完成 Operation 引用
- 已发布 Artifact 引用
- 后续可继续执行的必要状态
- 对应事件位置

Electron 启动时扫描遗留的 `RUNNING` 执行记录，将其置为可核对的中断状态。

**不能因为历史状态写着 RUNNING，就认定旧的模型请求仍然存活。**

恢复流程：

1. 读取最新可信 Checkpoint。
2. 检查绑定工作区及源文件状态。
3. 核对未确认的文件副作用。
4. 判断哪些阶段仍然有效。
5. 对不确定或需重新授权的操作进入等待状态。
6. 创建新的执行尝试，继续原 Task。

### 建议文件

- `main/agent/runtime/checkpoint-manager.ts`
- `main/agent/runtime/recovery-manager.ts`

### 验收标准

1. 强制退出客户端后，能够恢复同一个 Task。
2. 已完成的阶段和产物不无故丢失。
3. 工作区切换后，旧任务不能误操作新目录。
4. 输入文件变化后，能识别相关检查点可能失效。
5. 用户已拒绝或失效的授权不能被自动复用。

## P1-B01-T08：最小任务中心与 IPC

**优先级：P1**

### 设计任务

在 Electron 主进程建立安全的 Task API，并在 Vue 渲染进程提供最小任务中心。

第一版不追求复杂视觉设计。

功能必须包括：

- 创建任务
- 查看任务列表
- 查看任务详情
- 查看当前阶段
- 查看重要事件
- 查看任务状态
- 暂停或取消
- 恢复中断任务
- 展示操作确认
- 查看产生的文件

Renderer 应先读取持久化 Snapshot，再以事件序号订阅后续更新，避免因为窗口刷新而丢失关键状态。

Preload 必须使用明确、受限的 IPC 接口。Renderer 不直接持有 SQLite 连接，不直接执行文件工具。

### 建议文件

- `main/ipc.ts`（通过独立 handler 模块渐进接入）
- `preload/index.ts`
- `shared/preload-api.ts`
- `renderer/src/views/AgentTasksView.vue`
- `renderer/src/stores/agent-tasks.ts`

### 验收标准

1. 用户能看到新创建的任务。
2. 任务状态与 SQLite 持久化状态一致。
3. 页面刷新不丢失任务进度。
4. 重复订阅不会产生重复事件或副作用。
5. 不同用户不能控制他人的 Task。
6. UI 中能看清"正在执行、等待授权、异常中断、已完成"的差别。

# 第五部分：GitHub 提交与审查制度

## 1. 每批开发完成后提交的内容

建议采用独立功能分支，例如：

`feat/desktop-agent-p1-b01`

最终向 `main` 提交 PR。若当前只有单人开发，也可以提供合并后的具体 commit SHA，但优先保留 PR 的变更和测试记录。

每次提交审查至少提供：

| 项目 | 要求 |
|---|---|
| 分支或 PR | 明确代码审查范围 |
| Commit SHA | 锁定实际审阅版本 |
| 完成清单 | 对应本批 T01—T10 |
| 测试报告 | 实际运行命令、通过/失败情况 |
| 运行说明 | 如何启动与复现核心流程 |
| 关键截图或录屏 | 展示桌面端真实任务流程 |
| 已知问题 | 未完成项、技术限制、需要决策的事项 |

## 2. ChatGPT 的审查范围

当用户明确告知代码已经上传后，对指定 GitHub 提交执行：

**A. 架构审查**

- 是否符合三阶段总纲。
- 是否错误地引入第二套任务权威。
- 是否破坏已有 Agent、权限或工作区结构。
- 是否存在耦合、循环依赖或过度设计。

**B. 代码审查**

- Task/Run/Stage 边界。
- 事件与状态事务一致性。
- Operation Journal 与恢复幂等性。
- SQLite 用户隔离。
- IPC 安全和异常处理。
- 并发及竞态问题。

**C. 测试审查**

- 新测试是否真实覆盖要求。
- 是否存在假的通过、无效 Mock 或被跳过的检查。
- 是否有关键故障路径缺失。
- 是否能通过仓库现有测试与构建门槛。

**D. 验收审查**

逐个给出工单结论：

- **PASS：** 证据充分、满足当前验收。
- **PASS WITH NOTES：** 满足验收，但存在非阻断性改进。
- **BLOCKED：** 缺少运行或测试证据，暂不能验收。
- **FAIL：** 存在明确缺陷或不满足要求。

## 3. 审查后的推进规则

### 情况一：全部通过

冻结当前批次的契约基线，并发布：

下一批应基于真实提交后的最新架构设计，而不是机械套用今天的预案。

### 情况二：存在少量非阻断问题

发布简短修正清单。可以根据风险决定是否允许与下一批并行处理。

### 情况三：存在阻断问题

先发布：

**P1-B01-FIX — 审查整改批次。**

只列实际发现的问题、定位、复现步骤、修改要求与回归测试。

整改重新提交并审查通过后，再进入 P1-B02。

### 情况四：开发中形成更好的架构
