科研 Agent 产品设计与实现路线图
从“对话框 + 文件夹”升级为面向课题组的科研工作台
适用对象：高校课题组 / 研究生 / 科研助理 / 独立研究者
文档用途：产品规划、原型设计、开发排期、功能验收、后续商业化
核心建议：不要把产品目标定义成“做一个更像 Codex 的聊天窗口”。更有价值的方向是：把科研人员日常重复、繁琐、容易出错的流程做成可以一键启动、可检查、可追溯、可复用的科研任务。

0. 文档使用说明与总体结论
你当前已经具备一个很重要的起点：能够搭建 Agent 对话窗口、选择本地文件夹、让模型基于用户需求在工作目录中生成或修改代码，并可接入不同大模型。这说明“模型调用 + 本地文件操作 + 任务执行”这条基础链路已经可用。下一阶段不应继续堆聊天功能，而应把产品重点转向科研场景中的任务建模、结果交付、权限与可追溯性。
核心建议：最适合你的产品方向可以概括为：聊天只是入口，项目是载体，任务是核心，成果文件是最终交付物。
产品最终形态
首页不是一个空白聊天框，而是“今天要做什么科研任务”的任务中心。
每个课题建立独立 Project Space，统一管理论文、实验数据、代码、图表、笔记、引用和 Agent 产物。
Agent 不只“回答”，而是能创建成果：Word、Excel、图表、Markdown、LaTeX、Python/MATLAB 脚本、实验记录等。
每一次修改都可看到来源、依据、变更内容和生成文件，避免“模型说过但找不到”的问题。
对不懂 Prompt 的老师和同学，提供模板化任务、表单式输入和一键流程；对高级用户仍保留自由对话与工具调用。
支持类似实时语音助手的直接对话模式：用户可自然说话、随时打断、继续追问，并可用语音直接触发文献、数据、绘图、写作和实验记录任务。

1. 产品定位：从“科研版 Codex”到“科研工作台”
Codex 类产品最自然的用户是开发者，因为开发者能够把“我要什么”直接表达成代码任务，并且能判断 Agent 是否做对。科研用户则不同：很多老师、研究生并不知道该怎么把一个科研目标拆成 Prompt，更不会主动指定目录、文件格式、脚本运行方式。因此，如果只是复制“左侧文件树 + 中间聊天框 + 终端”的开发者界面，真正的科研用户会觉得功能强，但不知道从哪里开始。
1.1 产品的一句话定位
核心建议：一个面向课题组的 AI 科研工作台：把文献、数据、实验、写作、绘图、代码和汇报放进同一个项目空间，由 Agent 按科研任务自动完成可检查的工作流。
1.2 你真正应该卖的不是“大模型”
层次

结果层

用了多少参数的大模型
流程层
能否自动整理、核验、复现、继续修改
会不会“多轮聊天”

“AI 很聪明”
协作层
老师和学生能否共同查看、批注、接着做
复杂的 Agent 概念
1.3 核心差异化
科研任务模板化：把复杂 Prompt 隐藏在按钮、表单和流程背后。
项目上下文长期化：同一课题的资料、风格、术语、实验条件可以连续使用。
成果文件化：每个任务最终产出真实文件，而不是只留下聊天文本。
证据可追溯：关键结论能回到原论文页码、原数据行列、代码版本。
科研可复现：图表对应代码，统计对应数据，结论对应证据。
人机协作而非全自动：重要环节让用户确认，尤其是引用、实验条件、最终结论。

2.2 典型科研闭环
1. 建立课题：创建项目，填写研究目标、研究对象、关键词、目标期刊和团队成员。
2. 导入资料：论文 PDF、实验数据、图片、Word 草稿、代码、仪器导出文件。
3. 文献调研：形成文献矩阵、研究空白、方法对比和引用候选。
4. 实验与计算：生成实验方案、SOP、计算脚本或仿真参数表。
5. 数据处理：清洗、统计、拟合、绘图、异常值检查。
6. 论文写作：生成结构、补充证据、润色、引用核验、图注表注。
7. 组会汇报：自动把近期进展转换为 PPT 结构或会议摘要。
8. 归档复用：把最终数据、图、代码、结论和版本沉淀到项目知识库。
2.3 为什么“任务”要成为一级对象
传统聊天产品按“消息”组织，而科研工作更适合按“任务”组织。任务有明确的输入、步骤、产物、状态和验收标准。例如“生成 Figure 3”不是一句聊天，而是一个可复现任务：输入原始 Excel，执行数据清洗、拟合、绘图脚本，产出 PNG/PDF、代码和图注。

3.3 新手模式与专家模式
新手模式：按钮、表单、步骤向导，默认隐藏技术细节。
专家模式：允许直接写 Prompt、选模型、看工具调用、编辑系统提示词、运行终端。
两个模式共用同一底层任务系统，避免维护两套产品。

5. 文献研究 Agent
5.1 不要只做“PDF 聊天”
普通 PDF 聊天只能解决“这篇论文说了什么”。真正有价值的科研文献模块，要支持批量、比较、证据追踪和写作复用。

5.3 文献矩阵推荐字段
文献信息：标题、年份、期刊、DOI。
研究对象与场景：水体、污染物、设备、实验尺度等。
核心变量：自变量、因变量、控制变量。
方法：实验设计、模型、统计、表征仪器。
关键数值：效率、速率常数、粒径、浓度等。
作者结论：仅记录文献本身结论。
你的评价：优点、局限、与本项目关系。
可引用位置：支持哪一段论文、哪一个论点。
5.4 “引用防幻觉”必须成为产品卖点
核心建议：只要 Agent 生成了一个带参考文献的科研结论，就应该允许用户点击该引用，直接看到支持它的原文证据。无法定位证据的引用，应被标记为“待核验”，而不是悄悄输出。
6. 数据分析与科研绘图 Agent
这是最容易让用户立刻感受到价值的模块。科研人员往往不是不会分析，而是大量时间消耗在清洗数据、反复改图、统一格式和重新导出。
6.1 数据导入后的自动诊断
识别表头、单位、重复组、时间列、分类变量和缺失值。
检测异常值、空值、重复行、非数字字符、单位不一致。
判断数据是否适合做均值±标准差、箱线图、拟合、显著性分析等。
对任何自动修正都生成变更清单，原始数据永不覆盖。
6.2 推荐的绘图工作流
1. 用户选择数据文件。
2. Agent 识别变量并展示“我理解的数据结构”。
3. 系统推荐 2–4 种适合的图形，而不是直接盲画。
4. 用户选择期刊风格、尺寸、单位、字体。
5. Agent 生成图，同时生成 Python/MATLAB/R 代码。
6. 用户在 GUI 中调整图例、字体、轴范围、注释等。
7. 每次 GUI 修改同步回代码，确保图可以复现。
8. 一键导出 PNG/TIFF/PDF/SVG + 源代码 + 图注。

6.4 高级功能
上传一张目标期刊图，让 Agent 学习版式并重绘用户数据。
多子图自动排版：统一字母、边距、字体、图例位置。
自动检查是否存在坐标轴单位缺失、显著性标注错误、图中文字过小等问题。
同一项目中的所有图自动保持一致视觉规范。
7. 科研写作与引用核验 Agent
7.1 写作模块的正确定位
不要把它做成“AI 代写论文”。应该让它成为“证据驱动的科研写作编辑器”：写每一段时都能看到它使用了哪些项目数据、哪些文献和哪些已确认结论。
7.2 章节级功能
章节
Agent 可以做什么
Introduction
研究背景、研究问题、文献缺口、贡献结构检查
Methods
根据实验记录/SOP 生成可复现方法描述
Results
从已确认图表和统计结果生成客观描述
Discussion
与文献矩阵对比、解释一致与冲突、标注推测性内容
Conclusion
压缩主要发现，避免加入正文中没有证据的新结论
Abstract
从全文提取背景—方法—结果—结论，并检查数字一致性
7.3 三色证据系统
颜色/状态
含义
绿色：已证实
项目数据或文献中有明确证据
黄色：推断
基于证据进行合理推断，但需要作者确认
红色：无证据
当前项目中找不到支持，应删除、弱化或补充资料
7.4 版本对比
显示 Agent 修改前后差异。
区分语言润色与科学内容修改。
科学内容变化必须给出修改理由和依据。
允许逐条接受/拒绝，而不是一次性覆盖原文。
8. 实验设计、实验记录与 SOP Agent
如果你的产品主要服务课题组，这一模块会形成非常强的“实验室特色”。它能把科研 Agent 从通用写作工具变成真正进入实验流程的系统。
8.1 实验设计助手
输入研究目标、变量范围、可用设备和样品数量。
自动生成因素—水平表、对照组、重复次数、采样点建议。
生成试剂与耗材清单。
生成实验步骤、记录表和样品编号规则。
显式标记需要研究者确认的高风险参数，避免模型擅自决定。
8.2 电子实验记录（ELN）轻量版
记录项
示例

日期、操作者、项目、实验编号
条件
温度、压力、流量、pH、浓度等
设备
仪器型号、校准状态
过程
时间点、操作、异常情况
原始数据
仪器文件、照片、视频
结果
初步图表、备注
结论
当日确认结论/待验证问题
8.3 SOP 自动生成与版本控制
Agent 可以从实验笔记、论文方法和用户描述中生成 SOP，但必须保留版本号。后续用户调整某个条件时，应能自动提示：哪些历史实验使用了旧 SOP，哪些结果不能直接混合比较。
9. 代码、仿真与计算 Agent
这是你现有能力最接近的部分，因此可以作为底层执行引擎保留。区别是：不再要求科研用户理解目录、命令和脚本，而是由上层科研任务自动调用代码 Agent。
9.1 支持的任务类型
Python/MATLAB/R 数据处理脚本生成与运行。
LaTeX/Overleaf 公式与表格生成。
CFD/COMSOL/Fluent 等仿真前处理参数模板与结果后处理。
批量文件重命名、格式转换、目录整理。
科研计算公式转可执行脚本并生成验证样例。
从已有脚本中提取输入、输出、依赖并包装成可复用工具。
9.2 代码执行必须有“安全沙箱”概念
默认只允许访问当前项目目录。
删除、覆盖、大规模移动文件前要求确认。
联网、安装依赖、执行系统级命令应单独授权。
运行失败后保留日志，不要只告诉用户“执行失败”。
10. 组会、汇报与知识沉淀
10.1 自动生成“本周科研进展”
系统可以基于项目内最近一周的任务、文件和实验记录，自动整理“本周完成、关键结果、问题、下一步、需要导师决策的事项”。
10.2 一键生成组会材料
自动挑选最近新增的图和表。
生成每页 PPT 的标题、核心结论和讲稿。
将未解决问题单独列出，避免汇报只展示结果。
保留图表来源和版本，避免组会中拿错图。
10.3 实验室知识库
长期来看，可以把多个项目中已经确认的 SOP、仪器教程、常用脚本、绘图模板、审稿回复模板沉淀成课题组知识库。新生加入后不需要从头问师兄师姐，而是可以直接检索和调用标准流程。

任何失败步骤不应被隐藏，应该保留错误日志与可重试按钮。

19.2 “科研绘图”任务的完整交互示例
1. 用户点击“科研绘图”。
2. 选择一个 Excel 文件。
3. 系统显示：检测到 4 列数据，其中 Time 为连续变量，Treatment 为分组变量。
4. 系统提出：推荐折线图、散点+拟合、柱状+误差线三种方案。
5. 用户选择折线图，并选择“期刊风格”。
6. Agent 先生成预览，同时展示它使用的数据列和处理方式。
7. 用户在界面中调整字体、线宽、图例位置、轴范围。
8. 系统同步更新绘图代码。
9. 用户点击“完成”。
10. 项目中生成 figure_01.png、figure_01.pdf、figure_01.py、figure_01_caption.txt。
11. 任务详情记录所有输入与修改，后续可一键重新生成。
19.3 “文献综述”任务的完整交互示例
1. 用户点击“文献综述”。
2. 输入研究问题和关键词，或直接选择项目中的 PDF。
3. Agent 先建立筛选标准并显示给用户。
4. 批量解析文献，生成结构化文献卡片。
5. 按主题聚类并形成文献矩阵。
6. 提取一致结论、冲突结论、研究空白。
7. 生成综述大纲，每个小节绑定候选文献。
8. 用户点击某个结论，可以查看支撑原文。
9. 最终导出 review_matrix.xlsx、review_outline.docx、evidence_notes.md。
19.4 开发顺序建议（非常具体）
1. 先把“项目”数据结构做好：项目目录、元数据、文件索引、任务记录。
2. 把你现在已有的对话 Agent 嵌入项目，而不是单独存在。
3. 做统一的 Task 对象：输入、计划、状态、日志、输出文件。
4. 只做第一个任务模板：Excel → 绘图 → 导出图和代码。
5. 第二个任务模板做 PDF → 文献卡片 → 文献矩阵。
6. 第三个任务模板做“基于项目资料生成论文段落 + 引用证据”。
7. 等前三个任务稳定后，再开始做实验 SOP、组会、多人协作。
8. 当前三个核心科研任务稳定后，再加入实时语音层；语音本身不另造业务逻辑，而是复用已有任务系统和工具权限。
9. 最后才考虑开放任务市场、插件生态或复杂多 Agent。
20. 实时语音对话与语音科研助手（Voice Agent）
这一功能不是简单地在聊天框旁边加一个“语音转文字”按钮，而是给整个科研 Agent 增加一条新的交互通道：用户可以像和一个在身边的科研助理交谈一样，直接说话、听到回复、随时打断，并让语音对话真正调用项目、文件和科研工具。
核心建议：语音层应该复用你已经做好的项目、任务、工具和权限体系。文字聊天能做的科研任务，语音原则上都可以发起；需要高风险操作时，再切回可视化确认。
20.1 语音功能的产品定位
对于开发者，键盘输入 Prompt 很自然；但对导师、实验人员和不熟悉 Agent 的用户，直接开口往往更接近真实工作习惯。尤其在实验台前、会议中、看论文时或手上正在操作设备时，语音比文字更有优势。
场景
用户可能说的话
系统应该完成的事情
日常科研对话
“我刚才那个想法你再展开一点。”
理解上下文并继续讨论，而不是重新开始
实验现场
“记一下：0.35 MPa，取样时间 30 秒。”
写入当前实验记录并语音确认
数据分析
“把第三组数据画成折线图，误差棒保留。”
调用数据/绘图任务并生成成果包
论文阅读
“把这一段给我用中文解释一下，再说说它和我的项目有什么关系。”
读取当前文献位置，解释并关联项目资料
论文写作
“把刚才讨论的三点整理到 Discussion 的第二段。”
生成候选修改，显示差异后等待确认
组会准备
“总结一下我这周做了什么，给我讲一遍。”
读取项目进展并口头汇报，可同时生成文字摘要
灵感捕捉
“先记下来，暂时不要执行。”
保存为项目 Idea/待验证假设，而不是触发工具
20.2 用户应该获得怎样的“类似实时语音助手”体验
点击一次“语音”即可进入持续会话，不需要每说一句都按发送。
用户说话时实时显示转写文字，让用户知道系统听到了什么。
Agent 回复时采用流式语音播放，不必等完整答案生成完再开始说。
支持 Barge-in（随时打断）：Agent 正在说话时用户一开口，系统应立即停止当前播报并听取新指令。
支持自然停顿，不要用户稍微停一秒就误以为“说完了”。
同一语音会话保持项目上下文、当前打开文件、最近任务和刚才讨论内容。
可以在语音与文字之间随时切换；文字输入后，语音模式继续沿用同一上下文。
用户可选择只听简短回答，详细结果放在屏幕上，避免 Agent 连续朗读几分钟。

20.4 语音不只是“说话”，还要能驱动科研任务
真正有差异化的部分，是把语音会话和你前面设计的 Task 系统打通。语音 Agent 负责把自然语言转换成结构化任务，然后由原有工具链执行。
1. 用户说：“把今天 0.20–0.50 MPa 的实验数据整理一下，画出数量浓度随压力变化的图。”
2. 语音 Agent 识别目标，并在项目中查找今天的实验数据。
3. 系统口头确认关键歧义，例如：“使用 3-25-233 这一组数据，对吗？”
4. 用户说“对”。
5. 系统创建正式绘图 Task，在屏幕显示任务卡片和执行进度。
6. 绘图完成后，Agent 用一句话口头总结关键趋势，同时屏幕展示图、代码和图注。
7. 用户继续说：“把 0.35 MPa 那一点标出来，然后标题去掉。”
8. 系统修改候选图并生成新版本；历史版本仍保留。

组会/会议模式

20.6 实验现场语音模式：很适合做成你们课题组的特色
科研 Agent 最容易和通用 AI 拉开差距的地方，就是实验现场。研究生戴手套、拿移液枪、操作设备时，并不适合不停敲键盘。语音可以把“电子实验记录”真正变成低摩擦工具。
“开始实验，编号 O3-2026-09-27-03。” → 自动建立记录。
“压力调到 0.35 MPa。” → 写入当前步骤及时间戳。
“记一个异常：现在出水乳白程度比上一组高。” → 进入异常观察字段。
“30 秒取样完成，下一次 45 秒提醒我。” → 写记录并触发本地计时提醒。
“把刚才那张照片放到本次实验 T3 节点。” → 关联图片和时间点。
“实验结束，给我复述一遍今天有哪些异常。” → 自动汇总，但不擅自形成科学结论。
科研可信度要求：实验记录模式中，模型可以帮助整理，但“原始观测”与“AI 推断”必须分开保存。Agent 推测的原因不能混进原始实验记录。

20.8 “随时打断”应该怎样实现
打断是实时语音体验是否自然的关键。不能等 Agent 一大段话全部播完，用户才有机会发言。建议把“收音”和“播放”设计成可以同时存在的双向状态。
1. Agent 开始播报后，麦克风仍持续监听，但经过回声消除，尽量避免把扬声器声音识别成用户声音。
2. VAD 检测到用户真正开始讲话时，立刻降低/停止 TTS 播放。
3. 向会话管理器发送 interrupt 事件，取消尚未播放的语音片段。
4. 保留已说出的上下文，让模型理解用户是在“打断并修正”而不是开启新问题。
5. 如果打断内容是“停、算了、不要执行”，必须同时取消对应的待执行任务。

20.10 隐私与录音策略
麦克风状态必须始终可见，不能让用户不知道应用正在收音。
默认不永久保存原始音频；优先只保存用户确认的文字转写与任务记录。
如需保存会议录音，应在开始前明确提示并提供单独开关。
允许项目设置为“语音数据仅本地处理”或“允许云端语音模型”。
API Key 与语音服务凭证使用系统安全存储，不写入项目明文文件。
断网、识别失败或服务异常时，应能自动退回文字模式，不影响项目本身。
20.11 语音回复的内容策略
语音和文字不应机械地输出完全相同的内容。屏幕适合长表格、公式和详细推导，语音适合结论、解释和下一步。建议同一次 Agent 输出同时生成“屏幕完整版”和“口头摘要版”。
内容类型
语音怎么说
屏幕怎么显示
数据分析
“0.35 MPa 是当前峰值，我已经把图画出来了。”
完整图、数据、拟合、代码、统计
文献回答
先给 2–3 句结论
原文证据、页码、引用、详细对比
长推导
讲逻辑和结论，不逐字符读公式
完整公式与推导过程
错误
说明发生了什么和下一步
详细错误日志、重试按钮
20.12 实时语音 MVP 的开发顺序
1. 先做“按住/点击说话 → ASR 转文字 → 复用现有聊天 Agent → TTS 播放”，跑通最基本闭环。
2. 加入实时 partial transcript，让用户能看到识别过程并纠正专业术语。
3. 加入持续会话和自动 VAD，不再需要每句话点击发送。
4. 实现 TTS 流式播放，让回复尽快开口。
5. 实现 Barge-in 打断与取消播报。
6. 把语音意图接到现有 Task 系统：绘图、文献、记录等都由统一任务引擎执行。
7. 加入实验现场模式以及“快速记录”指令。
8. 最后再做多人会议、说话人区分、情绪/韵律等高级能力。

20.14 可以提前预留的高级语音能力
多语言科研对话：中文提问、英文术语保持准确发音，或中英文自由切换。
项目专业词典：自动学习课题组常用缩写、设备型号、化学物质和人员称呼。
会议说话人区分：自动整理“导师意见、学生回答、待办事项”。
耳机/移动端 companion：实验台旁用手机或耳机与桌面项目保持同一会话。
语音批注：看图时直接说“这里峰值标注太靠左”，自动转成图表修改任务。
主动播报但必须可控：例如长任务完成后提醒“Figure 3 已生成”，而不是频繁打扰用户。
个性化声音与语速：允许用户选择适合长时间科研使用的音色、语速和详细程度。
推荐落点：如果只选一个语音特色去做，建议优先做“实验现场语音记录 + 可追溯实验时间线”。它比单纯复制通用 AI 的语音聊天更有科研产品差异化，也更容易让课题组成员形成每天使用的习惯。
结语：你现在最应该做的一个决定
你现在已经有“Agent 能执行”的能力，下一步最关键的不是再接一个更强的模型，而是确定第一个真正值得科研用户每天打开的工作流。建议从你们课题组每天重复最多、结果最容易验收的工作开始，例如“Excel 数据 → 期刊风格图 → 可复现代码 → 图注”。
核心建议：第一版产品只要能让一个不懂 Agent 的研究生，在不写复杂 Prompt 的情况下，3–5 分钟完成一个过去需要 30–60 分钟的科研任务，就已经有非常明确的产品价值。
