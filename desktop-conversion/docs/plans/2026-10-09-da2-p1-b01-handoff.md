## 三、本批要做什么（DA2 P1-B01，T01–T10）

**目标一句话**：把现有会话式 Agent 扩展为**可靠、可持久化、可恢复的任务型 Agent**。
这是 Agent 2.0 的地基。

| 编号 | 任务 | 优先级 | 核心交付 |
|---|---|---|---|
| T01 | Agent 2.0 架构契约 | P0 | Task/Run/Stage/Operation/Approval/Artifact/Checkpoint 类型 + `AgentEventEnvelope` 事件 Envelope |
| T02 | SQLite 任务存储模型 | P0 | 8 张 `agent_*` 表（基于既有 `better-sqlite3` + `main/db/migrations.ts`） |
| T03 | Task 状态机与阶段执行契约 | P0 | 纯 TS 状态机，12 个状态，非法转移拒绝 |
| T04 | RunStore 与事件日志 | P0 | **状态更新与事件写入必须同一 SQLite 事务** |
| T05 | 工具 Operation Journal 与幂等保护 | P0 | `PREPARED → EXECUTING → COMMITTED`，故障走 `FAILED/UNKNOWN/RECONCILE_REQUIRED` |
| T06 | Checkpoint 与异常恢复 | P0 | 启动扫描遗留 `RUNNING`，恢复不重放副作用 |
| T07 | 现有 Agent Loop 兼容接入 | P0 | **适配，不是重写**；双路径（普通聊天 / 正式任务） |
| T08 | 最小任务中心与 IPC | P1 | Renderer 先读 Snapshot 再按 seq 订阅 |
| T09 | 专项测试与故障注入 | P0 | 12 个必测场景，见 DA2 原文表格。**路径补注**：DA2 建议 `apps/desktop/tests/agent-task-*.test.ts`，但实测现仓 **73 个测试文件全在 `tests/unit/` 一层**，无顶层散放先例 → 建议落 `apps/desktop/tests/unit/agent-task-*.test.ts`（vitest include `tests/**/*.test.ts` 两种都收，纯为随众） |
| T10 | 架构文档与交付证据 | P1 | `docs/desktop-agent-2/*.md` |

**开发顺序（DA2 第四部分，四组 + 四个检查点）**：

1. **第一组** T01→T02→T03→T04 → **检查点 A**：任务可创建/持久化/切状态/重启重读
2. **第二组** T05→T06 → **检查点 B**：模拟写入时崩溃，能核对恢复，不重复危险操作
3. **第三组** T07→T08 → **检查点 C**：桌面端跑通最小 Task，看到状态/工具事件/恢复结果
4. **第四组** T09→T10 → **最终检查点**：核心验收全过

## 四、红线（DA2 第四部分 §2 原文 + 本仓历史教训补强）

**DA2 明令不得引入**：

- 不替换现有用户认证体系
- 不修改 Server Agent 主执行架构
- 不删除现有聊天或工具历史
- 不开放无约束 Shell
- 不添加未经明确授权的数据上传
- 不将模型完整推理内容写入事件数据库
- 不在任务恢复时自动重放可能产生外部副作用的工具
- 不以大量历史兼容层作为捷径
- **不因为要加 Task Runtime 就一次性重写 `ipc.ts` 和现有 Agent Loop**

**父仓历史教训补强（写代码时特别小心）**：

- **`.delay()` 派发点要能区分"派发成功"与"worker 认领"** —— 只 log INFO 等于没校验；
  本仓有两条静默失效链路的历史（`index_meeting_chunks_task` 自 `d1aa07adb` 起漏注册、
  `index_drive_content_task` 自 `bd9c09bcf` 起漏注册）。见 CLAUDE.md 类 20.219。
- **心跳/存活状态绑「会话」不绑「UI 组件」** —— 全站 `<router-view>` 无 `<keep-alive>`，
  组件卸载即死亡；恢复路径必须与新建路径同样启动。见 CLAUDE.md 类 20.218（会议 255 事故）。
  **这条对 T06/T08 的恢复设计直接适用**。
- **新增 celery task 模块必须进 `celery_app.conf.imports`**（类 20.219）；桌面端对应物
  是 IPC handler 注册表 —— 新增 handler 要核它对否真被注册，别只看文件存在。
- **构建确定性**：`NODE_ENV` 与 Vite `mode` 是两个独立维度，build script 必须显式声明；
  禁止向构建产物注入 `Date.now()`/`process.pid` 等进程态值。见 CLAUDE.md W100 段。

## 七、审查制度要点（DA2 第五部分 §2/§3）

四个维度审查：**架构**（是否引入第二套任务权威/是否破坏既有结构/过度设计）、
**代码**（Task-Run-Stage 边界/事件与状态事务一致性/Operation Journal 幂等/SQLite 用户隔离/
IPC 安全/并发竞态）、**测试**（是否有假通过、无效 Mock、被跳过的检查、关键故障路径缺失）、
**验收**（逐工单给 PASS / PASS WITH NOTES / BLOCKED / FAIL）。

**给结论的判据**：`BLOCKED` = 缺运行或测试证据，暂不能验收。**别把"测试命令跑成功"
当成"异常恢复经过验证"** —— DA2 T10 验收标准原文点名了这一点。
