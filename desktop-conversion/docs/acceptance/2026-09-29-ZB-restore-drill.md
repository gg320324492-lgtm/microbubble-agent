## 设计级发现（待用户拍板，总指挥不擅动）

1. **「成员互相看不到」结构性失效**：服务端 2026-09 单一团队空间改造后 `create_file` **恒置 is_team_shared=True、入参忽略**（代码原话）——所有网盘内容（含备份容器+key.json）全组可见。容器虽加密，但钥匙就在旁边。二选一：① 服务端给 backups/ 目录做私有隔离；② key.json 不走网盘（改存服务器本地私密位置）。【用户 09-29 已知悉，方案待定】

   > **【已闭环 · 2026-09-30】** 用户裁决走方案①并加码。**真相分两层**：
   > ① ZB-1（`40b4b9883`+迁移140）复活了 `backups/` 保留区 private + 11 处写路径闸，但**验收查库发现生产中根本不存在该目录**——桌面端 `uploadFile` 丢弃目录信息，16 个真实备份全落根目录 team，**一条未保护**；
   > ② 更重的一层（ZB-1 未报，独立验收查出）：服务端为每个备份建 `kb` 孪生行（`drive_extracted`），**`key.json` 的密钥信封明文被抽取、已进向量索引**，且 `drive_to_kb_service.py:393` 存在 `private→team` 主动放大——**比原漏洞更严重**。
   > **ZB-2（`d357ad4b7`+`5e5d5d391`+迁移141）已闭环**：桌面端保留目录落 `backups/`、服务端备份形态在**两个任务入口**跳过抽取（孪生行 + 内容索引）、移除 `private→team` 翻转、迁移 141 清除 11 行孪生及其 chunks。
   > **实证**：kb 孪生 0 / 密钥 chunk 0 / 全部 13 条备份行 `private`。详见 `2026-09-30-ZB2-pass.md`。
   > **残留运维决策**：历史 key.json 明文若曾被读取，备份密钥轮换属运维动作，不在 ZB-2 范围。
2. **负责人本人从未被零感备份覆盖**：既有手工配置（R-9 时代）→ 四探针任一命中 → 按设计零覆盖跳过。需产品决策：设置页加「启用云端托管」开关，或对负责人档案定向迁移
3. **云备份只在登录时点火**：daily 调度（03:00）只跑本地备份，未接线云备份 → 长期挂机的机器云端容器会陈旧。需接线 daily → cloudBackup.runOnce
4. **可观测性黑洞**：备份失败走 Notification + `void catch(() => undefined)`，主进程日志零痕迹（本次 422 排查全靠服务器访问日志反推）。notifyFail 应同步 log
